METRICFLOW-KOTLIN · 엔진 가이드 · v1

metricflow 의미층 엔진 —
Kotlin 포팅의 작동 방식

이 문서는 metricflow 0.210.0의 Kotlin 포팅(metricflow-kotlin)을 큰 그림 → 데이터 흐름 → 코드 위치의 시점에서 설명한다. 의미층이 무엇인지부터 매니페스트가 SQL이 되기까지의 모든 단계를, 그 단계가 어느 Kotlin 파일에 살아 있는지와 함께 짚는다.

한 줄 요약

의미층 엔진은 "메트릭 정의 + 그룹 기준"을 받아 dialect별 SQL을 만들어내는 컴파일러다. metricflow-kotlin은 그 컴파일러를 7단계 파이프라인(manifest → transform/validate → query spec → semantic graph → dataflow plan → SQL plan → SQL string)으로 옮긴 결과물이며, SQL 실행은 의도적으로 외부에 맡긴다. 모든 단계는 sealed 타입 + visitor 패턴으로 닫혀 있고, 112개 corpus를 Python oracle과 byte-동등으로 통과한다.

01 · CONCEPT

의미층(semantic layer)이란 무엇인가

"같은 메트릭을 모든 팀이 같은 SQL로 묻는다"를 가능케 하는 컴파일러 계층이다. 지표(metric)와 차원(dimension)이라는 의미를 한 곳에 모아두고, 실제 SQL은 매번 생성한다.

왜 존재하는가

BI/분석 환경에서 같은 지표(예: bookings)를 두고 팀마다 다른 SQL을 쓰는 일이 흔하다. 조인 순서가 살짝 다르고, 필터를 빼먹고, NULL 처리가 어긋난다. 결과는 같은 이름의 숫자가 대시보드마다 어긋나는 것. 의미층은 이 변동성을 줄이기 위해 지표 정의를 코드로 외부화하고, 쿼리 시점에 결정적으로(deterministically) SQL을 생성해 일관성을 강제한다.

데이터 모델링 vs 데이터 의미

ETL/dbt는 모델링(테이블·뷰의 형태)을 다룬다. 의미층은 그 위에서 의미를 다룬다: 측정값(measure)이 어떻게 모이는가, 차원(dimension)이 어떻게 키(entity)로 연결되는가, 시간(metric_time)을 어떻게 통일하는가. metricflow는 dbt 0.x에서 출발해 독립 패키지로 분리된 의미층 엔진이며, Apache-2.0 라이선스로 풀 포팅이 가능하다.

metricflow-kotlin이 떠맡는 것 / 떠맡지 않는 것

엔진의 책임은 SQL 생성까지다. JDBC/웨어하우스 연결, 실행, 결과 페치는 외부 시스템의 몫이다. 이는 우연이 아니라 설계 결정으로, Python MetricFlowEngine.query()를 비롯한 모든 실행 어댑터(metricflow/execution/executor.py, SqlClient.query/execute/dry_run)는 Kotlin 포팅에서 의도적으로 제외했다. 자세한 근거는 CLAUDE.md "엔진 인터페이스 표면" 참조.

02 · BIG PICTURE

큰 그림 — 한 장의 다이어그램

입력은 두 개, 출력은 SQL 문자열 하나. 그 사이에 7단계 파이프라인이 있고, 각 단계는 다음 단계로 넘기는 중간 표현(IR)을 하나 만든다.

다이어그램의 7개 단계가 이 문서의 본문이다. 각 단계는 닫힌 입력 타입을 받아 닫힌 출력 타입을 내어놓는다. 단계 사이의 IR이 이 엔진의 핵심 어휘 — SemanticManifest, MetricFlowQuerySpec, DataflowPlan, SqlPlanNode, 그리고 마지막으로 String이다.

읽기 팁. 어떤 단계의 코드를 읽다가 "이 입력이 어디서 왔지?" 싶으면 위 그림으로 돌아오라. 각 단계의 출력 타입이 다음 단계의 입력이다. 단계 안에서 막막해지면 그 IR의 sealed hierarchy를 먼저 한번 훑는 게 답이다.

03 · OVERVIEW

데이터 흐름 7단계 개요

각 단계의 책임을 한 문단으로 요약하고, 입력/출력 타입과 핵심 Kotlin 파일을 표로 정리한다. 본문 §4–§11에서 같은 순서로 깊이 들어간다.

② TransformSemanticManifestcanonical SemanticManifestdomain/manifest/transformation/

각 단계가 한 일

  • ① 로드 — JSON을 kotlinx-serialization으로 SemanticManifest 데이터 클래스로 역직렬화. 외부 입력 신뢰 경계.
  • ② Transform — Pydantic JSON 직렬화 시 "사용자가 안 쓴 필드"를 채우는 단계. 14개 규칙. 예: SIMPLE 메트릭에 input_measure를 자동으로 채움.
  • ③ Validate — 의미적 정합성 검사. 28개 규칙 × 16개 파일. 예: agg_time_dimension이 실제로 존재하는 시간 차원인지.
  • ④ Parse — 사용자 입력 문자열("listing__country")을 DimensionSpec 등 정형 타입으로 해석. 의미 그래프와 협업.
  • ⑤ Dataflow — 어떤 조인·필터·집계가 필요한지를 23-종 노드 DAG로 표현. 아직 SQL은 모른다.
  • ⑥ Plan Conversion — 각 dataflow 노드를 SQL plan 노드 트리로 변환하는 23-arm visitor.
  • ⑦ Render — SQL plan을 dialect별 문자열로 출력. 8개 dialect는 DefaultSqlPlanRenderer의 작은 override들.

왜 IR이 둘인가? Dataflow plan과 SQL plan을 분리한 이유는 관심사 분리다. Dataflow는 "의미적으로 어떤 데이터 흐름이 필요한가"를 표현하고, SQL plan은 "구문적으로 어떤 SELECT/JOIN/WHERE 트리가 되는가"를 표현한다. 한 dataflow 노드(예: AggregateSimpleMetricInputsNode)는 여러 SQL 표현(SUM(x) vs COUNT(DISTINCT x))으로 갈리고, 한 SQL 표현은 여러 dataflow 노드의 공통 출력일 수 있다. 분리해야 깨끗하다.

04 · MANIFEST

의미 매니페스트 — 모든 것의 입력

SemanticManifest는 의미층 엔진의 "스키마"다. semantic model(원천 테이블), 그 위의 measure·dimension·entity, 그것들로 빚어진 metric, 그리고 saved query를 한 데 묶은 JSON 문서.

최상위 구조

SemanticManifest는 네 개의 리스트 + 한 개의 설정으로 끝난다. Python PydanticSemanticManifest의 1:1 포팅이며, kotlinx-serialization을 통해 JSON과 round-trip한다. 

// modules/core/.../domain/manifest/model/SemanticManifest.kt
@Serializable
data class SemanticManifest(
    val semanticModels: List<SemanticModel>,
    val metrics: List<Metric>,
    val projectConfiguration: ProjectConfiguration,
    val savedQueries: List<SavedQuery> = emptyList(),
)

5종의 핵심 도메인 타입

data class

SemanticModel

물리 테이블 한 개에 대응. nodeRelation(데이터베이스·스키마·테이블), measures, dimensions, entities를 묶는다. "이 테이블에서 측정 가능한 것은 무엇인가"의 선언.

data class

Measure

집계 가능한 컬럼. name, agg(SUM/AVG/COUNT/…), expr(원천 SQL식), agg_time_dimension. 모든 메트릭의 원자 단위.

data class

Dimension

그룹 키. type=CATEGORICAL이면 listing__country 같은 분류 차원, type=TIME이면 ds처럼 granularity와 함께 다루는 시간 차원.

data class

Entity

조인 키. type=PRIMARY|UNIQUE|FOREIGN|NATURAL. semantic model 간 JOIN이 어떻게 일어날지를 결정.

discriminated record

Metric

한 record에 type: MetricType(SIMPLE/RATIO/CUMULATIVE/DERIVED/CONVERSION) + 광폭 typeParams. Python에서 Pydantic이 하나로 합쳤기 때문에 Kotlin도 sealed로 가르지 않고 record 모양을 보존했다.

예: 작은 manifest 발췌

// 한 semantic model — fct_bookings 테이블 위에 measure 1 + dim 2 + entity 1
{
  "name": "bookings_source",
  "node_relation": { "schema_name": "mf_corpus", "alias": "fct_bookings",
                     "relation_name": "mf_corpus.fct_bookings" },
  "measures": [
    { "name": "bookings", "agg": "sum", "expr": "1", "agg_time_dimension": "ds" }
  ],
  "dimensions": [
    { "name": "ds",      "type": "time", "type_params": { "time_granularity": "day" } },
    { "name": "country", "type": "categorical" }
  ],
  "entities": [
    { "name": "booking",  "type": "primary", "expr": "booking_id" },
    { "name": "listing",  "type": "foreign", "expr": "listing_id" }
  ]
}

이 한 모델에서 자동으로 도출되는 group-by 후보: ds의 granularity 변형 (ds__day/week/month/...), country, listing을 따라 JOIN한 cross-model dimension들 (예: listing__country).

테이블 스키마와의 매핑 — JSON이 실제 SQL의 무엇을 가리키는가

위 manifest는 텍스트일 뿐이다. 실제 DB에 두 테이블이 있다고 하자. 의미층은 이 두 테이블 위에 의미를 얹는다. 

-- 실제 DDL (Trino dialect 기준). 이 위에 의미 모델을 얹는다.
CREATE TABLE mf_corpus.fct_bookings (
    booking_id      BIGINT,         -- 한 booking을 식별 (primary entity)
    listing_id      BIGINT,         -- 어느 listing인지 (foreign entity, JOIN 키)
    guest_id        BIGINT,
    ds              DATE,           -- booking 시각 (time dimension, agg 기준)
    country         VARCHAR,        -- booking 시점의 국가 스냅샷 (categorical dimension)
    booking_value   DECIMAL(18,2),
    is_instant      BOOLEAN
);

CREATE TABLE mf_corpus.dim_listings (
    listing_id      BIGINT,         -- listing의 row identity (primary entity)
    user_id         BIGINT,         -- 호스트 user (foreign entity)
    country         VARCHAR,        -- listing의 현재 국가 (categorical dimension)
    created_at      TIMESTAMP,      -- listing이 만들어진 시각 (time dimension)
    is_lux          BOOLEAN,
    capacity        INT
);

같은 country가 양쪽에 있지만 의미가 다르다. fct_bookings.country는 booking 시점의 스냅샷이고, dim_listings.country는 listing의 현재 값이다. 두 컬럼은 이름은 같아도 의미가 달라 — 사용자가 group-by로 어떤 걸 의도하는지가 중요해진다. 이게 cross-model dimension의 의미적 가치다.

그러면 manifest의 각 JSON 필드가 위 DDL의 어디를 가리키는지 — bookings_source 모델 기준:

manifest JSON 필드실제 SQL 위치역할
node_relation.relation_name mf_corpus.fct_bookings 테이블 이 모델이 보는 row source. FROM 절에 그대로 들어간다.
entities[booking].expr = "booking_id" fct_bookings.booking_id 컬럼 한 행 = 한 booking. primary entity. (semantic graph에서 노드 식별자 역할)
entities[listing].expr = "listing_id" fct_bookings.listing_id 컬럼 foreign entity. dim_listings의 primary entity와 매칭되어 JOIN 키.
measures[bookings].agg = "sum", expr = "1" 컬럼 아님 — 식 SUM(1) "booking 개수" 메트릭의 원자. expr은 컬럼명이 아니라 임의의 SQL 식이다.
measures[bookings].agg_time_dimension = "ds" fct_bookings.ds 컬럼 같은 모델의 time dim 이름을 가리킨다. cumulative/time-spine 쪽에서 기준 컬럼.
dimensions[ds] type=time, time_granularity="day" fct_bookings.ds 컬럼 day 입자. ds__week/month/...는 SQL DATE_TRUNC로 자동 도출.
dimensions[country] type=categorical fct_bookings.country 컬럼 group-by 가능. "booking 시점 스냅샷" 의미는 manifest에 명시되어 있지 않다 — 모델러의 책임.

manifest는 컬럼 목록이 아니다. fct_bookings 테이블에 guest_id, booking_value, is_instant 컬럼이 더 있지만 manifest엔 안 나온다 — 사용 안 하는 컬럼은 선언하지 않으면 그만이다. 반대로, SUM(1)처럼 컬럼이 아닌 식도 measure가 될 수 있다. manifest는 "테이블의 어떤 부분에 어떤 의미를 부여할지"의 화이트리스트일 뿐이다.

짝이 되는 두 번째 모델 — listings_source

cross-model 쿼리(예: group_by=['listing__country'])가 가능하려면 두 번째 모델이 필요하다. dim_listings 위에 얹는 의미 모델은 이렇게 생긴다: 

// listings_source — dim_listings 테이블 위에 dim 3 + entity 2 (measure 없음, 순수 차원 모델)
{
  "name": "listings_source",
  "node_relation": { "schema_name": "mf_corpus", "alias": "dim_listings",
                     "relation_name": "mf_corpus.dim_listings" },
  "dimensions": [
    { "name": "country",    "type": "categorical" },
    { "name": "is_lux",     "type": "categorical" },
    { "name": "created_at", "type": "time", "type_params": { "time_granularity": "day" } }
  ],
  "entities": [
    { "name": "listing", "type": "primary", "expr": "listing_id" },
    { "name": "user",    "type": "foreign", "expr": "user_id" }
  ]
}

측정값(measure)이 없어도 의미 모델이 될 수 있다 — 이런 모델은 차원만 공급하는 "lookup" 역할. 핵심은 entities[listing]의 type: "primary": bookings_source의 foreign entity와 이름·표현식이 매칭돼 자동 JOIN 키가 된다.

자동으로 풀리는 쿼리 — 의미층의 가치 한 장면

두 모델이 manifest에 같이 들어 있을 때, 사용자가 다음 쿼리를 보내면: 

// 사용자 입력 (MetricFlowQueryRequest)
{ "metric_names": ["bookings"],
  "group_by_names": ["listing__country", "metric_time__day"] }

엔진은 manifest를 보고 다음 SQL을 만들어낸다 (개념적으로): 

-- 의미 그래프가 자동으로 풀어준 JOIN
SELECT
  l.country               AS listing__country,
  DATE_TRUNC('day', b.ds) AS metric_time__day,
  SUM(1)                  AS bookings
FROM mf_corpus.fct_bookings  b
JOIN mf_corpus.dim_listings l
  ON b.listing_id = l.listing_id   -- entity 매칭으로 자동 도출
GROUP BY 1, 2;

사용자가 직접 쓰지 않은 것: FROM, JOIN ... ON, SUM(1), DATE_TRUNC('day', ...), alias 이름. 이걸 manifest에서 풀어주는 게 의미층 엔진의 일이다. listing__country의 dunder 표기는 "listing entity를 따라가서 country dimension"이라는 의미. 의미 그래프(§7)가 이 경로를 찾는다.

자주 헷갈리는 부분 — 네 가지 질문

Q1. entity.expr는 컬럼명 외에 뭐가 들어갈 수 있나? 그냥 column이라고 안 하는 이유는?

expr은 컬럼명이 아니라 SQL 식(expression)이다. 가장 흔한 케이스는 컬럼명 한 단어 (expr: listing_id)지만, 식이 들어가는 케이스도 있다:

  • 복합 키 — expr: "CONCAT(account_id, '_', region_id)"처럼 여러 컬럼을 합쳐 한 entity를 만든다.
  • COALESCE — expr: "COALESCE(user_id, anonymous_id)"로 NULL을 흡수.
  • cast / 정규화 — expr: "LOWER(email)"같이 표면적 다양성을 한 entity로 모은다.
  • 생략(Optional) — Pydantic 정의가 expr: Optional[str] = None. 생략하면 name이 컬럼명으로 쓰인다. 즉 { "name": "booking" }만 적으면 booking이라는 컬럼을 가리키게 된다.

Q3. agg_time_dimension은 정확히 무슨 역할인가?

한 measure가 "어느 time dimension을 기준으로 시간 위에 잘리는지"를 가리키는 필드. 한 semantic model에 시간 차원이 여러 개 있을 수 있고 (booking 시각 ds, 결제 시각 paid_at 등), 각 measure는 그중 하나를 "내 시간 축"으로 선언한다.

코퍼스 예 — bookings_source:

defaults:
  agg_time_dimension: ds          # 이 모델의 default time axis

measures:
  - name: bookings
    agg: sum
    expr: "1"                     # default ds 따라간다

  - name: booking_payments
    agg: sum
    expr: booking_value
    agg_time_dimension: paid_at   # 결제 기준으로 잘림 — override

booking_payments를 metric_time__day로 group-by하면, 엔진은 fct_bookings.paid_at을 day 단위로 자른다 — ds가 아니라. 이게 같은 모델에서 두 종류의 시간 axis가 공존하는 패턴.

구체적으로 어디서 쓰이나:

  • metric_time 별명 라우팅 — 사용자가 metric_time__day로 group-by하면 metricflow는 이 measure의 agg_time_dimension 컬럼을 골라 자른다. 사용자는 모델별 컬럼 이름 (ds인지 paid_at인지)을 몰라도 된다.
  • CUMULATIVE 메트릭 — "최근 30일 합계" 같은 윈도우 계산은 이 컬럼을 기준 시간으로 잡고 time spine에 join.
  • time spine join — 비어있는 날짜를 채울 때 이 컬럼이 spine과 매칭된다.

기술적으로 agg_time_dimension은 같은 모델 안의 time dimension 이름이어야 한다 (validation rule AggregationTimeDimensionRule이 검사). 다른 모델의 dim은 불가 — 그러면 의미가 모호해진다.

설계 평가 — metric_time이 단순 편의인가, 구조적 추상화인가

중요한 의문: "그냥 time dimension으로 명시 정의된 것만 dim 목록으로 노출하면 안 되는가? 왜 metric_time이라는 별도 추상이 필요한가?" 핵심을 먼저 말하면 — metric_time은 사용자 편의가 아니라 엔진 내부의 구조적 transform이다.

코드가 그 증거다. MetricTimeDimensionTransformNode의 docstring:

# python_oracle/upstream/metricflow/dataflow/nodes/metric_time_transform.py:17
"""A node transforms the input data set so that it contains the metric time

이 노드는 dataflow plan의 모든 explain 경로에 들어간다. measure의 agg_time_dimension 컬럼을 읽어, 데이터셋의 그 컬럼을 metric_time이라는 통합 이름으로 alias하는 게 본 역할. 즉 엔진 내부에선 모든 measure가 metric_time이라는 단일 시간 축을 공유한다 — 사용자가 그 이름을 쓰든 안 쓰든.

그래서 효용을 실제로 받는 5가지 사용처:

  1. Cross-measure 시간 정렬 (가장 큰 가치). bookings(uses ds) + booking_payments(uses paid_at)를 한 쿼리에 묻고 day 단위로 그래프를 그릴 때 — 사용자는 metric_time__day 하나만 group-by에 쓴다. 엔진이 measure마다 자기 agg_time_dimension을 골라 day로 자른다. "explicit time dim만 dim 목록에 있다"면 사용자가 measure마다 어느 컬럼인지 알아야 하고, measure를 합칠 때 어느 측 시간을 쓸지 명시해야 한다.
  2. CUMULATIVE 메트릭의 윈도우 정의가 시간 컬럼 이름에 의존하지 않는다. trailing_2_months_revenue의 metric YAML은 window: 2 month만 적힌다 — 컬럼 이름 무관. 시간 축은 txn_revenue measure의 agg_time_dimension에서 implicit 도출. 만약 explicit time dim 모델이었다면 cumulative 정의에 "time_dimension: ds_recv"를 또 적어야 한다. metric 정의가 모델 details에 짙게 묶이는 결과.
  3. Time spine fill의 라우터. 비어있는 날짜에 0을 채워 시각화하려면 모든 measure의 시간 컬럼을 spine과 join해야 한다. metric_time이 통합된 spine 칼럼 이름이라 한 번에 join. 없으면 measure별 별도 join 로직 필요.
  4. DERIVED 메트릭의 time offset (예: month-over-month). metric_time 위에서 "1 month 뒤로"라는 논리가 깔끔. measure 컬럼 이름이 달라도 metric 정의는 추상 시간 위에서 균일.
  5. SQL 옵티마이저 — 단일 GROUP BY. plan_conversion 단계가 모든 measure를 같은 metric_time 컬럼으로 group한다 → single SELECT으로 합쳐짐. 분리된 time dim이면 measure별 sub-query를 outer join해야 한다 — 코드 + SQL 모두 복잡.

우아한가? 평가

장점:

  • 여러 measure를 한 쿼리에 묶을 때 시간 정렬이 zero-config
  • Cumulative / DERIVED 메트릭 정의가 모델의 컬럼 이름에서 독립 — metric layer가 데이터 모델 변화에 robust
  • 엔진 내부에서 단일 GROUP BY 통합 — SQL이 단순
  • 학습 곡선 평탄: 사용자는 metric_time__day 하나만 알면 됨

단점:

  • "숨겨진 매직" — 처음 보면 metric_time이 어디서 왔는지 헷갈림. 디버깅 시 어느 measure가 어느 시간 컬럼으로 라우팅됐는지 추적 필요
  • 구현 비용 — MetricTimeDimensionTransformNode라는 dedicated 노드 + validation rule. dataflow plan의 추가 단계.
  • 한 measure에 진짜로 두 개 의미적 시간 축이 있는 경우 (created_at AND completed_at 모두 분석 가치) — 한 쪽만 primary로 선언 가능. 다른 쪽은 일반 time dim으로만 노출되고 metric_time 라우팅에선 빠진다.
  • 모델러의 책임 가중 — measure의 agg_time_dimension이 의미적으로 맞는지를 모델러가 정확히 알아야 함. 잘못 지정하면 "왜 내 cumulative 메트릭이 잘못 잘리지?" 디버깅이 길어진다.

결론: 단일 metric · 단일 dashboard라면 over-engineered다 — Cube의 explicit 방식이 더 직관적. 하지만 여러 metric을 한 캔버스에서 동시 분석하는 메트릭 layer로 보면 metric_time의 abstraction이 강력한 지렛대를 만든다. metricflow가 명시 dim보다 추상 dim을 택한 건 "metric layer로서의 정체성"을 우선한 결정이고, 트레이드오프는 분명히 존재하지만 설계 의도와 일관된다고 평가할 수 있다.

이게 의미층의 가장 중요한 설계 결정이다: entity name은 project 전체의 식별자다. 두 모델이 entities[listing]을 선언했으면 metricflow는 같은 개념의 listing을 가리킨다고 본다 — 모델 이름은 무관.

그래서 foreign entity가 어떤 모델의 entity인지 명시하지 않는다. 그냥 name이 매칭되는 다른 모델의 PRIMARY/UNIQUE entity로 자동 JOIN된다:

      expr: listing_id

  dimensions:  [ ds, created_at, country, capacity_latest, is_lux_latest, ... ]

  name: lux_listing_mapping
  node_relation: { alias: dim_lux_listing_id_mapping }
  entities:

      expr: listing_id

서로 다른 두 물리 테이블(dim_listings_latest와 dim_lux_listing_id_mapping)이 각자 listing을 primary로 선언한다. 같은 listing 개념을 공유하지만, 노출하는 dimension/측정값은 다르다. listings_latest는 listing의 기본 속성(country, capacity 등), lux_listing_mapping은 listing → 럭셔리 매핑 다리 역할.

왜 이런 패턴이 가치 있나:

  • 한 entity의 attribute가 데이터웨어하우스에서 여러 테이블에 흩어져 있는 게 정상이다 — listing 기본 정보 테이블, 호스트 정보 테이블, lux 매핑 테이블, 좌표 테이블, 등등. 한 거대 테이블로 합치는 건 ETL 비용·갱신 주기 충돌·storage 비용 문제로 어렵다.
  • 각 테이블을 자기 측의 의미 모델로 만들고 entity name으로 묶으면, 사용자는 listing__country(listings_latest에서) / listing__lux_listing__some_field(lux_listing 거쳐) 같은 dim을 자연스럽게 쓸 수 있다.
  • SemanticGraphBuilder가 listing이라는 단일 entity 노드를 만들고, 두 PRIMARY 모델을 그 노드에 잇는 엣지로 연결한다. 쿼리 시점에 어느 모델에서 dim을 가져올지를 그래프가 자동 선택.

한 테이블을 두 SM으로 쪼개는 경우는?

기술적으로 가능하지만 흔하지 않다. 같은 테이블에서 다른 의미 그룹을 분리할 때 정도 — 예컨대 한 테이블에 "raw 측정값"과 "비즈니스 KPI"가 같이 들어있고, raw는 엔지니어 모델·KPI는 비즈니스 모델로 분리하고 싶을 때. 보통은 measure를 한 모델에 몰아놓고 metric으로 분리하는 게 깔끔. 권장 패턴은 "하나의 entity 컨셉 × N개 물리 테이블 → N개 의미 모델"이지 "하나의 테이블 → N개 의미 모델"이 아니다.

검증 규칙은 무엇을 막나

그럼 metricflow는 같은 이름 PRIMARY 중복을 그냥 허용하나? 검증 규칙이 의미적 일관성은 검사한다:

  • NaturalEntityConfigurationRule — 같은 이름 entity가 모델 간 type이 일관된지. 한 곳에선 PRIMARY인데 다른 곳에선 NATURAL이면 에러. (PRIMARY vs UNIQUE vs FOREIGN은 섞일 수 있지만 NATURAL은 특수)
  • DimensionConsistencyRule — 같은 이름 dimension이 모델 간 type·granularity·expr이 일치하는지.
  • PrimaryEntityRule — 각 모델에 primary entity가 있거나 (직접/유도) 명시되어 있는지.

중요한 것: 같은 entity name이 두 PRIMARY로 등장하는 자체는 에러가 아니다. metricflow의 설계 의도. 단, 의미가 정말 같은 entity인지는 모델러의 책임 — 두 테이블의 listing_id가 정말 같은 universe의 ID여야 한다 (한 쪽은 internal ID, 다른 쪽은 marketplace ID처럼 다르면 JOIN이 잘못된 결과를 낸다).

2홉의 의미 — corpus 실 예시

corpus의 multi_hop_join_manifest가 정확히 2홉 chain의 표준 예다. 세 모델로 구성: 

# account_month_txns.yaml — 출발 (메트릭이 있는 fact 테이블)
semantic_model:
  name: account_month_txns
  node_relation: { alias: account_month_txns }
  measures:    [ txn_count ]
  entities:

# bridge_table.yaml — 중간 다리
semantic_model:
  name: bridge_table
  node_relation: { alias: bridge_table }
  dimensions:  [ extra_dim ]
  entities:
    - { name: account_id,  type: primary }    # ← account_id로 first hop
    - { name: customer_id, type: foreign }    # → customer_id로 second hop

# customer_other_data.yaml — 도착 (분석 대상 dim)
semantic_model:
  name: customer_other_data
  node_relation: { alias: customer_other_data }
  dimensions:  [ country, ... ]
  entities:
    - { name: customer_id, type: primary }    # ← customer_id의 master

이때 사용자가 metric_names=['txn_count'] + group_by=['account_id__customer_id__country']를 요청하면, 엔진은 자동으로: 

SELECT
  c.country                                                 AS account_id__customer_id__country,
  SUM(a.txn_count)                                          AS txn_count
FROM account_month_txns a
JOIN bridge_table          b  ON a.account_id  = b.account_id     -- 1-hop
JOIN customer_other_data   c  ON b.customer_id = c.customer_id    -- 2-hop
GROUP BY 1;

group-by 이름의 dunder 분절을 세면 정확히 account_id · customer_id · country — entity link 2개 + 마지막 dimension. 이게 2홉의 상한.

왜 2홉으로 제한했나

코드의 에러 메시지가 "not yet supported"라고 적어둔 데서 알 수 있듯, 영구 제한은 아니고 보수적 디폴트다:

  • SQL 폭발 방지. hop마다 JOIN이 추가된다. 5홉이면 5번의 JOIN + 각 hop의 fan-out 위험. 사용자가 의도하지 않은 polynomial blowup이 발생할 수 있다.
  • 모호성 제거. 깊은 chain일수록 같은 entity name이 그래프 안에서 여러 경로로 도달 가능 — 어느 경로를 택할지 disambiguation 규칙이 복잡해진다. recipe_writer_weight.py의 가중치 시스템이 이걸 풀려 노력하지만, 깊이를 키울수록 모서리 케이스가 늘어난다.
  • 사용자 mental model. listing__country(1홉)은 직관적, account__customer__country(2홉)는 아직 따라간다. 3홉 이상은 그래프 토폴로지를 외워야 — 보통은 모델러가 중간 join을 한 모델로 미리 마련하는 게 더 깔끔.
  • 경로 폭발. PathEnumerator(W11)가 DFS로 모든 경로를 탐색 — 그래프 크기 × 깊이로 시간이 늘어난다. 2가 실용적 손익분기점.

Malloy의 nested query — 사실 JOIN을 안 쓰는 패러다임

위 표에서 "Malloy = nested query 패러다임"이라고 했는데 좀 단순화된 표현이다. 정확히는 Malloy(Google의 Looker 창립자 팀이 만든 오픈소스 SQL 대체 언어)는 JOIN을 1차 시민이 아니라 source 정의의 일부로 빼고, 분석 쿼리는 중첩(nested) 결과를 직접 표현한다.

핵심 개념 셋:

  • Source — 테이블 + 미리 선언된 measure/dimension/join. metricflow의 semantic_model에 비슷한 자리.
  • Nested query (turtle) — 쿼리 안에 쿼리를 박는 1차 문법. 결과가 평평한 표가 아니라 계층 JSON.
  • Aggregating locality — 각 집계가 "어느 source에서 집계되는지"를 컴파일러가 자동 추적. JOIN 후 fan-out으로 SUM이 잘못 부풀려지는 흔한 버그가 원천 차단.

구체 예 — "각 customer 별로, status별 주문 수"를 Malloy에서:

// Malloy
source: users is table('users') extend {
  join_many: orders on users.id = orders.user_id    // JOIN은 source에 선언
  measure: user_count is count()
}

run: users -> {
  group_by: state
  aggregate: user_count

  nest: orders_breakdown is orders -> {            // 중첩 쿼리 — 결과가 계층
    group_by: status
    aggregate: order_count is count()
  }
}

출력은 평평한 row가 아니라 이런 모양:

{
  "state": "CA", "user_count": 1240,
  "orders_breakdown": [
    { "status": "completed",  "order_count": 8910 },
    { "status": "cancelled",  "order_count":  430 }
  ]
},
{
  "state": "NY", "user_count": 980,
  "orders_breakdown": [ ... ]
}

SQL로 같은 결과를 만들려면 (1) users-orders JOIN 후 state로 GROUP BY (2) 별도 쿼리로 status별 GROUP BY (3) 두 결과를 애플리케이션에서 합치기 — 또는 한 쿼리에 GROUPING SETS / window function의 복잡한 조합. Malloy는 이걸 한 표현으로 푼다.

metricflow와의 차이:

  • metricflow: 사용자가 metric_names + group_by를 주면 엔진이 평평한 row의 SQL을 만든다. JOIN은 entity name 매칭으로 자동 추론.
  • Malloy: 사용자가 결과 모양 자체를 쿼리로 기술. JOIN은 source 정의에 미리 있어, 쿼리는 "어떤 source에서 무엇을 집계할지"만 적는다. 결과는 계층 구조.
  • 두 시스템 다 "사용자가 JOIN ON 절을 쓰지 않는다"는 공통점은 있지만, metricflow는 그래프에서 자동 추론, Malloy는 source 정의에서 declarative.

그래서 Malloy에 "JOIN 깊이 제한"이라는 개념이 없는 건, 깊이 제한이 적용될 대상이 없기 때문에 가깝다. 분석 쿼리는 source가 제공하는 attribute만 쓰고, source에 join이 더 필요하면 source 정의를 확장한다. 깊이는 모델러가 어디까지 source에 합쳐 뒀느냐의 함수다.

metric layer 자체는 Malloy의 1차 관심사가 아니다 — Malloy는 SQL 대체 언어로서 분석 표현력 자체를 끌어올리는 데 무게. metricflow는 metric 정의·검증·다중 차원 dispatch에 집중. 같은 분석 도메인이지만 해결하려는 문제의 결이 다르다.

3홉이 필요하면 어떻게 하나

실무적 해법 — 중간 join을 모델 한 개로 미리 합치는 것:

  • DW에서 ETL로 customer_with_account_summary 같은 derived 테이블을 만들고 단일 SM으로 노출 → 1홉이 됨
  • 또는 dbt model 단에서 join한 view를 만들고 그 위에 SM 정의

즉 metricflow는 "그래프가 알아서 풀어주는 JOIN은 2홉까지, 그 이상은 데이터 모델링 단계에서 풀어달라"는 stance. 이건 metric layer로서 의도된 디자인 — 데이터 모델 복잡도를 SQL 시점에 떠넘기지 않는다.

참고: corpus의 third_hop_table.yaml은 존재한다 (3-hop 시나리오 fixture). 하지만 실제 쿼리 corpus엔 third_hop_count metric이 account_id__customer_id__country(2홉)까지만 group-by한다. 3홉을 직접 요청하는 테스트는 "이 케이스는 supported가 아님을 확인"하는 negative test다.

05 · TRANSFORM + VALIDATE

변환과 검증 — manifest를 canonical하게

JSON으로 들어온 manifest는 그대로는 의미 그래프에 못 넣는다. Pydantic 시절 입력 친화적으로 생략 가능했던 필드를 채우고(transform), 의미적으로 어긋난 곳을 찾는다(validate).

14개 변환 규칙 — 왜 필요한가

Python PydanticSemanticManifestTransformRuleSet이 정의한 14개 규칙을 DefaultTransformRuleSet이 그대로 옮겼다. 핵심은 "사용자가 안 쓴 표현을 명시 표현으로 푸는" 것:

  • ConvertCountRules — agg: count가 expr 없이 들어오면 COUNT(1)로 채움.
  • ConvertMedianRules — agg: median은 percentile 0.5의 alias로 매핑.
  • FlattenSimpleMetricsWithMeasureInputs — SIMPLE 메트릭의 입력 측정값을 펼쳐 후속 단계에서 재참조 가능하게.

  • FixProxyMetricsRule — measure를 alias로 노출하는 "proxy metric"을 사후 정리.
  • RemovePluralFromWindowGranularityRule — cumulative.window: "30 days"를 30 day canonical로.

모든 규칙은 SemanticManifestTransformRule 인터페이스를 구현하며, 순서대로 primary → secondary 두 세트로 묶여 차례로 실행된다. 출력은 같은 SemanticManifest 타입이지만 canonical한 형태.

MetricFlowQueryParser.parseAndValidateQuery는 얇은 dispatch (naming scheme 선택 + saved query 펼치기)만 하고, 실제 일은 MetricFlowQueryResolver.resolveQuery (~520 LOC, Phase 3 W14a에서 본체 포팅)가 한다.

  • naming scheme — 입력 문자열을 DunderNamingScheme / MetricNamingScheme / ObjectBuilderNamingScheme 중 매칭되는 스킴으로 dispatch.
  • resolution DAG 빌드 — 쿼리 입력을 QueryResolutionNode 트리로 변환 (각 group-by 항목·필터·order-by가 노드).
  • group-by item 해석 — 의미 그래프 resolver(§7)에 위임해 각 dunder name을 정확한 LinkableInstanceSpec으로.
  • where filter 해석 — WhereFilter의 Jinja 템플릿을 WhereFilterSpec으로.
  • metric spec 생성 — 메트릭 이름이 실재하는지 검사 + dependency expand.
  • order-by 검증 — 모든 order item이 group-by 또는 metric 안에 있는지.
  • time constraint expand — 시작·끝 문자열을 TimeRangeConstraint로.
  • input order 보존 — 사용자가 준 순서를 InputSpecOrder로 기록 (SELECT 컬럼 순서 결정).
  • issue aggregation — 모든 resolver issue를 한 결과 객체로 묶어 반환.

실패 시에도 throw가 아니라 queryResolution.hasErrors == true로 반환. MetricFlowEngine.explain에서 이 깃발을 보고 IllegalArgumentException으로 끌어올린다.

07 · SEMANTIC GRAPH

의미 그래프 — 엔진의 핵심 무기

"이 메트릭에서 도달 가능한 group-by 항목은 무엇인가?"를 답하는 자료구조. 파서, dataflow 빌더, listDimensions/entitiesForMetrics 등 거의 모든 RPC가 의존한다.

노드와 엣지

SemanticGraph는 방향성 그래프. 노드는 8종의 entity-node + 3종의 attribute-node로 총 11종(sealed). 엣지는 entity-link, joined-model, metric-definition 등을 표현. metric 노드에서 시작해 attribute 노드까지 가는 path가 곧 "그 메트릭에서 이 group-by 항목으로 가는 SQL 경로"다.

예시 해설: bookings 메트릭은 bookings_source 모델에 살고, 그 모델에서 ds 시간 차원과 country 카테고리 차원에 직접 닿는다. listing 엔터티 링크를 따라가면 listings_source 모델로 JOIN하면서 그 모델의 차원에도 닿는다. 그래서 listing__country가 multi-hop dimension으로 surface 된다.

DFS path-aware resolver (W11)

attribute resolver는 그래프에서 모든 경로를 DFS로 훑는다. 각 경로는 AttributeRecipe 하나로 압축 — 어떤 entity link를 거쳤고, 어떤 model에서 시작·끝났고, 어떤 dunder name을 만들었는지. 같은 attribute에 둘 이상의 경로가 있으면 trie의 "ambiguity-erases" 규칙으로 둘 다 폐기 (사용자가 모호한 이름을 쿼리할 수 없다).

W11 이전에는 BFS reachability만 썼는데 multi-hop 시나리오에서 join chain을 잃는 문제가 있었다. path-aware DFS로 바꾸면서 corpus가 54→81 PASS로 점프.

AnnotatedSpec과 GroupByItemSet

  • AnnotatedSpec — "spec + 어디서 왔는지 + 어떤 properties를 갖는지". properties는 LOCAL, JOINED, MULTI_HOP, ENTITY, DATE_PART, METRIC_TIME, DERIVED_TIME_GRANULARITY 등 메타 플래그.
  • GroupByItemSet — 한 메트릭에 대해 도달 가능한 모든 group-by item을 trie 형태로 담는다. 다중 메트릭 쿼리에선 set들이 intersect 된다 (모든 메트릭에서 도달 가능해야 group-by 허용).

08 · DATAFLOW PLAN

Dataflow Plan — 추상 실행 계획

의미적으로 "어떤 데이터 변환이 필요한가"를 표현하는 DAG. 23종 노드, 단일 sink, 부모 → 자식 방향으로 데이터 흐름.

기반 추상

모든 노드는 DataflowPlanNode(abstract class)를 상속하며 두 가지 필수 멤버를 갖는다: nodeId(자동 발급되는 식별자)와 parentNodes. 두 노드는 모든 필드가 같아도 다른 객체면 다르다 — identity equality. "같은 일을 하는 노드인가"를 알고 싶으면 functionallyIdentical()를 따로 호출 (Python functionally_identical 포팅). 

// modules/core/.../domain/dataflow/DataflowPlanNode.kt
abstract class DataflowPlanNode(parentNodes: List<DataflowPlanNode>) :
    DagNode<DataflowPlanNode>(parentNodes) {

    open val inputSemanticModel: SemanticModelReference? get() = null
    open val aggregatedToElements: Set<LinkableInstanceSpec> get() = emptySet()

    abstract fun <R> accept(visitor: DataflowPlanNodeVisitor<R>): R
    abstract fun functionallyIdentical(other: DataflowPlanNode): Boolean
    abstract fun withNewParents(newParents: List<DataflowPlanNode>): DataflowPlanNode
}

09 · PLAN CONVERSION

Plan Conversion — Dataflow → SQL Plan

Dataflow의 23종 노드를 SQL plan 트리로 옮기는 visitor. 각 dataflow 노드 한 개가 보통 SqlSelectStatementNode 한 개로 매핑되며, 부모 dataflow 노드는 자식 SELECT의 FROM 서브쿼리가 된다.

두 계층

DataflowToSqlPlanConverter는 top-level이지만 일은 거의 안 한다 — 진짜 일은 DataflowNodeToSqlSubqueryVisitor가 한다 (23개 visitXxxNode 메서드). Converter는 visitor를 만들고, sink 노드로 dispatch한 결과를 받아 ConvertToSqlPlanResult로 포장한다.

fun convertToSqlPlan(
    sqlEngineType: SqlEngine,
    dataflowPlanNode: DataflowPlanNode,
    optimizationLevel: SqlOptimizationLevel,
    sqlQueryPlanId: DagId?,
    outputColumnOrderer: OutputColumnOrderer,

    val visitor = DataflowNodeToSqlSubqueryVisitor(...)
    val root: SqlDataSet = dataflowPlanNode.accept(visitor)

SqlDataSet — 노드 간 caller-callee 인터페이스

각 visitXxx는 SqlDataSet을 반환한다. 이건 "이 dataflow 노드의 출력은 어떤 SqlPlanNode 트리(보통 SELECT)이고, 그 SELECT의 각 출력 컬럼이 어떤 Instance(metric/dimension/entity)에 대응하는가"를 묶은 record. 부모 노드의 결과를 자식이 받아 FROM으로 wrapping한다.

SqlDataSet.sqlPlanNode이 노드의 SQL 출력 (보통 SqlSelectStatementNode)
SqlDataSet.instanceSet각 컬럼의 의미적 정체 — 어떤 metric/dimension/entity spec이며, 어떤 column name으로 노출되는가
bindParametersWHERE 절 등에 등장한 SQL bind parameter들 (where filter spec에서 누적)

예: AggregateSimpleMetricInputsNode → SqlSelectStatement

  • 부모 dataflow 노드의 SqlDataSet을 받아 자기 FROM 절로 사용.
  • group-by 키로 SELECT 절에 dimension 컬럼 추가.
  • 각 measure에 대해 SUM(...) / COUNT(...) / PERCENTILE_CONT(...) 등 expr 생성.
  • GROUP BY 절 추가.

10 · SQL PLAN + RENDER

SQL Plan과 렌더링 — 마지막 변환

SQL plan은 SELECT/JOIN/WHERE 트리의 추상 표현이다. 5개 plan-node + 24개 expression-node로 모든 SQL을 그려낸다. 렌더러는 그 트리를 문자열로 떨군다.

두 가지 sealed 계층

왜 SQL 실행을 안 하는가

Python MetricFlowEngine.query()는 SqlClient의 execute()를 호출해 결과 DataFrame을 돌려준다. Kotlin 포팅이 이것을 의도적으로 뺀 이유:

  • 관심사 분리 — 의미층 엔진의 책임은 SQL을 만드는 것까지. 실행은 어차피 외부 DB 연결, 인증, 모니터링, retry, 캐싱이 얽힌다.
  • monomer 도메인 — 운영 환경에서는 별도의 SQL 실행 인프라가 있고 거기에 SQL을 넘기는 게 자연스럽다.
  • 테스트 가능성 — 실행 결과를 비교하지 않고 SQL 문자열을 비교하면 dialect 7개 × corpus 112개를 byte-동등으로 검증 가능.

입력

// MetricFlowExplainRequest

groupByNames      = ["metric_time__day"]

timeConstraintStart, End = null

manifest는 simple_manifest fixture — bookings_source 모델 + bookings SIMPLE 메트릭. corpus에서는 corpus/explain__simple__bookings_by_metric_time__all_dialects/request.json.

단계 1–3 (manifest load → transform → validate)

  • SemanticManifest 데이터 클래스로 역직렬화 — 모든 28개 검증 issue가 없음을 확인.
  • 14개 transform 규칙 적용 후 SIMPLE 메트릭의 input_measure가 자동 채워짐.
  • SemanticManifestLookup이 한 번 만들어지고, SemanticGraph가 lazy 빌드.

단계 4 (parse)

MetricFlowQueryParser.parseAndValidateQuery → MetricFlowQueryResolver.resolveQuery:

  • "bookings" → MetricSpec(name="bookings").
  • "metric_time__day" → DunderNamingScheme으로 dispatch → time dimension trie 매칭 → TimeDimensionSpec(name="metric_time", timeGranularity=DAY, entityLinks=[]).
  • resolution issue 0개 — MetricFlowQuerySpec 생성.

단계 5 (dataflow plan)

DataflowPlanBuilder.buildPlan(querySpec) — SIMPLE 분기 (§8 그림과 동일):

  1. ReadSqlSourceNode(bookings_source) — leaf.
  2. MetricTimeDimensionTransformNode(ds → metric_time).
  3. AggregateSimpleMetricInputsNode(SUM(__bookings), GROUP BY metric_time__day).
  4. WriteToResultDataTableNode — sink.

단계 6 (plan conversion)

DataflowToSqlPlanConverter.convertToSqlPlan(plan, SqlEngine.DUCKDB):

  • sink가 accept(visitor)를 호출, visitor가 부모를 재귀로 방문.
  • 각 dataflow 노드가 SqlSelectStatementNode로 변환 — 부모는 FROM 절의 서브쿼리.
  • SqlColumnPrunerOptimizer가 미사용 컬럼 제거 — bookings_source의 다른 measure들은 select에서 빠진다.
  • SqlTableAliasSimplifier가 1회 alias를 inline (subq_1, subq_2가 사라짐).
  • 결과 SqlPlan(sqlPlanNode = SqlSelectStatementNode(...)).

단계 7 (render → SQL string)

-- Compute Metrics via Expressions
-- Write to DataTable
SELECT
  metric_time__day
  , SUM(__bookings) AS bookings
FROM (
  -- Read Elements From Semantic Model 'bookings_source'
  -- Metric Time Dimension 'ds'
  -- Select: ['__bookings', 'metric_time__day']
  -- Select: ['__bookings', 'metric_time__day']
  SELECT
    DATE_TRUNC('day', ds) AS metric_time__day
    , 1 AS __bookings
  FROM mf_corpus_2026_05_11_static.fct_bookings bookings_source_src_10000
) subq_3
GROUP BY
  metric_time__day

주석은 SqlSelectStatementNode의 description이 dialect renderer의 prefix-comment 단계에서 직접 쏟아낸다. subq_3 alias는 SequentialIdGenerator의 3번째 발급 — 결정적이므로 corpus가 byte-매치된다.

같은 입력, BigQuery로 dialect만 바꾸면

DATE_TRUNC('day', ds) 한 줄만 DATETIME_TRUNC(ds, day)로 바뀐다. 나머지는 동일. 이게 dialect 분리의 가치 — plan은 dialect-agnostic, 차이는 expr renderer 한 곳에 응축.

차등 테스트로 정답 보장

Python oracle을 정답으로, 같은 112개 입력에 대해 byte-동등을 강제한다. "테스트 통과"가 아니라 "Python과 같은 SQL을 만드는가"가 합격 기준.

corpus 구조

corpus/<case-name>/ 하나마다:

  • request.json — manifest + MetricFlowExplainRequest를 한 파일에.
  • meta.json — subcommand, dialect, fixture name 등 메타.
  • expected/<dialect>.sql 또는 expected.json — Python이 생성한 정답.

총 112 케이스 × 평균 ~3 dialect = 298 SQL/JSON expected. 8개 subcommand (explain, explain_get_dimension_values, list_metrics, list_dimensions, entities_for_metrics, list_group_bys, list_saved_queries, validate_manifest) 전부 커버.

diff-runner

modules/internal-tests/diff-runner — Gradle :internal-tests:diff-runner:run로 실행. 각 케이스에 대해:

  1. request.json을 SemanticManifest + MetricFlowExplainRequest로 역직렬화.
  2. Kotlin MetricFlowEngine을 in-process로 호출.
  3. 출력 SQL을 SqlNormalizer의 3가지 규칙(line endings, trailing whitespace, blank lines)으로 정규화.
  4. expected 파일과 byte-동등 비교.
  5. 실패 시 첫 mismatch의 line + column + JSON path까지 보고.

JSON 출력은 더 까다롭다 — Python json.dumps와 Kotlin kotlinx-serialization은 insertion order가 다를 수 있으므로, 키를 알파벳 정렬하고 식별 키로 리스트도 정렬한 다음 비교. 식별 키 매핑은 CaseRunner.LIST_KEYS_WITH_SORT_KEY에 하드코딩.

왜 SQL 실행을 포팅하지 않았나

실행은 환경 의존적이다 — JDBC URL, 인증, 커넥션 풀, 모니터링, retry, 캐싱, 사용자 권한이 모두 외부 시스템 책임. 엔진은 SQL 문자열을 결정적으로 만드는 데 집중하고, 그 SQL을 누가 어떻게 실행할지는 호출자가 결정.

부산물로 테스트 가능성이 폭발적으로 좋아진다 — 실행 결과 (DataFrame)를 비교하지 않고 SQL 문자열을 비교하면 정답 확정·corpus 관리·dialect 비교 모두 결정적이다.
