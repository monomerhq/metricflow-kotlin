RESEARCH · STRATEGIC · DECISION DOC

오픈소스 시맨틱 레이어 비교 —
MetricFlow를 계속 갈 것인가

Kotlin 포팅을 112/112 PASS로 마친 시점에서, customize 단계 진입 전 출발점을 한 번 다시 평가한다. 후보는 MetricFlow, Cube, Malloy, Lightdash, Rill, Boring Semantic Layer. 비교 기준은 표현력·use case 커버·성숙도, 그리고 우리 상황에 특화된 customize fit.

한 줄 요약

MetricFlow를 그대로 간다. 2025년 10월 Apache 2.0 재라이선스 + 같은 달 Open Semantic Interchange(OSI) 표준의 참조 구현으로 채택된 사건이 MetricFlow의 거버넌스 무게중심을 dbt Cloud 단독에서 산업 컨소시엄(Snowflake·Salesforce·Cube·Hex 등 30+사)으로 옮겼다. Cube는 기능적으로 가장 풍부하지만 엔진이 아니라 실행 인프라(pre-aggregation 클러스터)에 가까워 우리 책임 경계(SQL 생성까지)와 어긋난다. Malloy는 새 언어이고, Lightdash/Rill은 BI 도구라 비교 대상이 다르다. 우리가 만든 자산 (8M+ 토큰, 60k LOC 풀 포팅, corpus 100%)은 OSI 표준의 JVM 참조 구현으로 자연스럽게 승격된다. 피벗하지 말 것.

01 · WHY THIS DECISION

이 결정이 왜 중요한가

지금 출발점을 잘못 골랐다면 비용은 customize 단계 내내 누적된다. Kotlin 포팅을 끝낸 시점은 customize 자유도가 가장 큰 순간이자, 동시에 다른 base로 갈아탈 매몰비용이 아직 0이 아닌 마지막 시점이다.

현재 투자 상황

2026-05-17 기준 누적 자산은 PROGRESS.md 기준:

풀 포팅 범위도달 가능 60,346 LOC / 477 files (metricflow 0.210.0)
Kotlin 산출 규모약 10 publishable modules, ~436 .kt 파일
차등 테스트corpus 112/112 PASS (Python oracle ≡ Kotlin SQL, normalizer 적용 후 strict 100%)
dialect 커버8개 (Trino · BigQuery · Snowflake · Databricks · Redshift · DuckDB · Postgres · Default)
검증 규칙28개 SemanticManifestValidator 규칙 풀 포팅
누적 에이전트 토큰약 8.6M (오케스트레이터 + builder + evaluator 합)
지나간 mission cycle30+ (Phase 0 → Phase 5 모듈 컨솔리데이션 완료)

결정의 비대칭성

두 가지 비용을 같은 척도로 본다.

  • 머무르는 비용 — customize 항목별로 MetricFlow 도메인 모델 위에 확장 작성. 매 항목마다 corpus 회귀가 새 안전망이 됨.
  • 갈아타는 비용 — 8.6M 토큰의 작업이 매몰비용이 됨 + 새 base의 풀 포팅을 다시(혹은 다른 형태로) 해야 함 + 새로운 corpus 마련.

매몰비용 함정 경계. "이미 많이 했으니 계속 가자"는 그 자체로는 논거가 아니다. 만약 다른 base가 우리 use case에 명백히 더 잘 맞는다면 8.6M 토큰을 잃더라도 갈아타는 게 옳다. 이 문서는 그 판단을 정직하게 내리기 위한 것이다.

02 · CONTEXT

시맨틱 레이어란 무엇인가 (간략 재정리)

자세히는 docs/explained/metricflow-engine.html에 정리되어 있다. 비교를 위한 정의만 한 번 짚는다.

시맨틱 레이어는 "메트릭의 정의를 코드로 묶고, 쿼리 시 어떤 dimension으로 dispatch할지를 엔진이 결정하게 하는 계층"이다. 사용자는 메트릭 이름과 group-by 이름만 던지고, 엔진이 join 경로·시간 grain·집계 순서를 풀어 SQL을 만든다. dbt MetricFlow의 도메인 어휘로는 semantic manifest → spec resolution → dataflow plan → sql plan → dialect render.

구별이 흐려질 수 있는 경계 셋:

  • 시맨틱 레이어 ≠ BI 도구. 시맨틱 레이어는 SQL을 만들기까지(혹은 API로 서빙). BI 도구는 그 위에 시각화를 얹는다. Lightdash·Rill은 BI 도구이면서 안에 시맨틱 레이어를 품는 형태.
  • 시맨틱 레이어 ≠ 쿼리 가속기. Cube의 pre-aggregation 레이어처럼 캐싱·재구체화는 부가 책임. MetricFlow는 의도적으로 그 책임을 안 진다.
  • 시맨틱 레이어 ≠ 쿼리 언어. Malloy는 새 query language. SQL을 대체하려는 야심. MetricFlow는 기존 SQL을 생성한다.

이 세 축의 위치가 비교의 핵심 차원이다.

04 · DEEP DIVE

MetricFlow 심층 분석

"메트릭을 일급 시민으로 다루는, dbt-style 코드형 SQL 생성 엔진." 2023년 dbt Labs가 Transform Data를 인수해 흡수. 2025년 10월 Apache 2.0 재라이선스 + OSI 표준의 참조 구현 채택이 가장 큰 사건.

철학과 trade-off

MetricFlow의 핵심 선택은 "엔진은 SQL 생성까지, 실행은 외부"다. warehouse 안의 어떤 엔진(BigQuery·Snowflake·Trino…)이라도 그대로 쓰고, 엔진은 메트릭 정의의 해석과 SQL로의 정확한 컴파일에만 책임을 진다. Cube가 자체 캐시 클러스터를 끌고 오는 것과 정반대.

값(values) 정렬:

  • 정확성 > 성능. fan-out / chasm join을 entity type으로 정적으로 막는다. 성능은 warehouse 책임.
  • 코드형 정의 > UI 정의. 모든 게 YAML + git PR. UI는 dbt Cloud로 분리.
  • 호환성 > 발명. SQL 그대로 출력. 새 언어/새 프로토콜 도입 안 함.
  • 도메인 어휘 보존. semantic_model, metric, entity, measure, metric_time — Pydantic 모델 그대로.

모델링 언어

파일 포맷은 YAML. 개념 모델은 다음과 같이 분리되어 있다.

semantic_model1개 dbt 모델(테이블)에 대응. measures + dimensions + entities를 포함
entityprimary / unique / foreign / natural 타입. 자동 join 그래프의 노드
measureaggregation 표현식 (sum/count/avg/median/percentile/sum_boolean/count_distinct)
dimensioncategorical 또는 time. time은 grain 지정
metricsimple / ratio / cumulative / derived / conversion 5종
metric_time모든 메트릭이 공유하는 가상 time dimension. 메트릭별 time dim을 통합
saved_query재사용 가능한 쿼리 + export (table/view) 매핑

time 처리는 이 분야에서 가장 정교하다. metric_time__day / __week / __month ... 식으로 grain dispatch가 일급 문법. cumulative 메트릭은 time spine 테이블에 자동 join하여 누적 윈도우를 푼다.

join 모델은 "entity name 매칭으로 자동 해소". 사용자가 join 경로를 직접 쓰지 않고, primary/foreign entity 타입으로 fan-out을 정적으로 회피. 최대 2-hop까지 지원하는 점은 알려진 제한 (multi-hop을 더 깊게 가려면 별도 semantic model이 필요).

엔진 아키텍처

파이프라인:

Kotlin 포팅이 그대로 따라간 구조이며, 우리 모듈 분할(domain.manifest → domain.spec.bind → domain.dataflow → domain.sql.plan → infrastructure.sql.render.{dialect})이 이 파이프라인을 1:1 반영한다.

출력 인터페이스

  • SQL 문자열 (dialect별) — 우리 포팅의 핵심 산출.
  • 실행계획 메타 — MetricFlowExplainResult: querySpec, dataflowPlan, sqlPlan, outputSqlTable.
  • 카탈로그 RPC — listMetrics / listDimensions / listGroupBys / listSavedQueries / entitiesForMetrics.
  • SQL 실행은 의도적 제외. SqlClient의 실행 메서드는 정의조차 없음.

알려진 약점

  • 전역 이름공간. entity / dimension / measure / metric의 이름이 프로젝트 전체에서 unique. total_sales 두 도메인 = parse error.
  • 2-hop join limit. MAX_JOIN_HOPS=2 하드코딩.
  • 쿼리 시점 계산만. 캐싱/pre-aggregation 없음 — warehouse 비용 그대로.
  • dimension은 primary entity가 있는 모델에서만. primary key 없는 event log는 dimension으로 join 불가.
  • 0.x 버전. 1.0 미릴리즈. 마이너 버전 사이 모델 변경이 가능 (단 2026년 OSI 표준화 흐름이 이 변동성을 줄일 가능성).
  • 학습 곡선. entity 타입 / metric_time / time spine 등의 개념을 같이 익혀야 함.

05 · DEEP DIVE

Cube 심층 분석

"엔진 + pre-aggregation 캐시 클러스터를 묶은 universal semantic layer." 오픈소스 시맨틱 레이어 중 가장 큰 별 수(20k)와 가장 넓은 API 표면. 단 이는 "엔진"보다 "인프라"에 가깝다.

철학과 trade-off

Cube의 핵심 선택은 "메트릭을 API로 서빙하면서, 사이에 캐시를 박는다"이다. Cube Store(Rust, RocksDB + Apache Parquet + Arrow) 클러스터가 pre-aggregation을 보관하고, Cube Server(Node.js)가 REST / GraphQL / SQL / Python API로 메트릭을 노출한다. 결과: 임베디드 대시보드의 sub-second 응답을 warehouse 비용을 늘리지 않고 달성.

값 정렬:

  • 성능 ≈ 정확성. pre-aggregation으로 sub-second 50–500ms, 100–1000 QPS.
  • API breadth. REST / GraphQL / SQL / Python — 임베디드 분석의 핵심.
  • 다양한 frontend. 데이터 앱·고객 대시보드·LLM agent 모두 같은 API.
  • 인프라 부담을 받아들인다. Cube Store + Redis + worker — 운영 대상.

모델링 언어

파일 포맷은 YAML 또는 JavaScript(둘 다 1급). 개념 모델은 다음과 같다.

cube1개 테이블/뷰에 대응. dimensions + measures + segments + joins를 포함
viewcube 위에 facade를 만들어 메트릭 + dimension subset을 외부에 노출
dimensionstring / number / boolean / time. time은 grain 지원
measurecount / sum / avg / min / max / count_distinct / running_total 등
joinone_to_one / one_to_many / many_to_one. LEFT JOIN 고정. 사용자가 명시적으로 SQL 표현 작성
segment재사용 가능한 미리 필터 (predefined WHERE)
pre_aggregationmaterialized rollup 정의. Cube의 핵심 기능

MetricFlow와의 가장 큰 차이: cube가 dimension/measure를 직접 품는다는 점. MetricFlow는 semantic_model(데이터)과 metric(정의)을 분리하고 entity로 연결. Cube는 cube 안에 join을 명시적으로 쓴다.

엔진 아키텍처

파이프라인은 두 단계로 갈라진다.

  • API → SQL/Cube Store: 쿼리가 들어오면 미리 정의된 pre-aggregation 중 매칭되는 것이 있으면 Cube Store에서 직접 응답. 없으면 warehouse로 fall-through하여 LIVE SQL 생성·실행.
  • Pre-aggregation builder: 백그라운드에서 warehouse → Cube Store로 rollup을 주기적으로 적재. Parquet 컬럼 포맷, RocksDB 메타.

Cube는 SQL을 생성하지만, 그 SQL이 어디로 가는지에 대해 엔진이 결정권을 가짐 — Cube Store 또는 warehouse. 즉 실행 책임을 엔진이 가져간다는 게 MetricFlow와 결정적으로 다른 지점.

출력 인터페이스

  • SQL API (Postgres-호환 wire protocol) — BI 도구가 Cube를 Postgres처럼 본다.
  • REST API — 가장 일반적, embedded 분석의 표준.
  • GraphQL API — 정해진 measure/dimension 조합 쿼리.
  • Python API — ML/DS 사용 케이스.
  • MCP server — LLM agent용 (Cube가 OSI 컨소시엄 참여).

알려진 약점

  • 운영 부담. Cube Store + Redis + worker — 5명짜리 팀에 부담일 수 있음.
  • 학습 곡선. pre-aggregation 설계가 까다로움. fan-out 처리 + grain alignment를 사용자가 이해해야.
  • Pre-aggregation 유지 비용. 모델 변경 = pipeline rebuild. 대시보드 수가 늘수록 maintenance 폭증.
  • Time/metric_time 추상화 약함. grain dispatch는 cube의 time dimension granularity로 풀지만, MetricFlow의 metric_time 같은 메트릭 간 공통 추상화는 없음.
  • Cumulative / conversion metric 표현력. 가능하지만 사용자 SQL 작성 비중이 큼 — MetricFlow처럼 selector로 처리되지 않음.
  • Cube Cloud로의 풀. 핵심 기능(엔터프라이즈 access control 등) 일부가 Cloud 전용.

핵심. Cube는 우리 포팅과 책임 경계가 다르다. 우리가 가져가는 책임은 SQL 생성까지. Cube는 그것에 더해 캐시 인프라 + API gateway까지. 우리 사용 케이스가 사실 Cube를 향해 있다면 피벗을 고려할 가치가 있지만, 명시된 미션(Monomer Control의 Semantic module에 SQL 생성 코어를 공급)은 그렇지 않다.

06 · DEEP DIVE

Malloy 심층 분석

"SQL을 대체하려는 새 쿼리 언어." Looker 창업자 Lloyd Tabb이 Google에서 시작한 프로젝트. 시맨틱 모델링과 쿼리를 같은 언어 안에 묶고, nested data를 1급으로 다룬다. 2025년 Linux Foundation 산하로 이관.

철학과 trade-off

Malloy의 핵심 선택은 "SQL이 가린 것을 다시 드러낸다"이다. 구체적으로:

  • Nested data 보존. JSON → flatten은 의미를 잃는다. nest: 키워드로 하위 쿼리를 결과 안에 nesting.
  • Symmetric aggregates. fan-out 시 sum/avg 오류를 언어 차원에서 자동 회피.
  • Semantic model = query language. LookML처럼 분리하지 않고 같은 .malloy 파일에서.
  • Free + safe. SQL의 자유 + LookML의 안전성을 둘 다 가져가려는 야심.

Lloyd Tabb의 주장은 명확하다: "Looker의 시맨틱 모델은 UI를 위한 것이었고, 결과적으로 business user의 것이 되었다. data developer는 무시당했다. Malloy는 data developer를 위한 proper language다."

모델링 언어

파일 포맷은 .malloy 전용 DSL. VS Code extension이 1차 IDE.

source테이블/쿼리에 대한 의미적 wrapper. dimension / measure / join / view를 포함
view재사용 쿼리 정의. nest: 가능
measureaggregation 표현식. SQL function 호환
dimensionfield 또는 SQL 표현식
join_one / join_many관계 명시. symmetric aggregate가 fan-out 자동 처리
nest결과 안에 sub-result. 가장 독특한 특징

예: group_by: state aggregate: total_sales nest: top_products is { ... } 같이 nested query를 결과로 받는다. SQL에서 flatten하던 작업을 모델이 처리.

엔진 아키텍처

Malloy compiler(TypeScript, 98%)가 .malloy를 dialect-specific SQL로 변환. 실행은 Connection.runSQL()이 적절한 backend에 보냄. 지원 dialect: BigQuery, Snowflake, PostgreSQL, MySQL, Trino/Presto, DuckDB, Databricks, MSSQL.

출력 인터페이스

  • SQL (dialect별) + 실행 결과 (Connection이 실행까지).
  • Notebook (.malloynb) — Malloy 셀 + 결과 (Jupyter-스타일).
  • VS Code extension이 1차 IDE.

알려진 약점

  • 새 언어 습득 부담. SQL을 모르는 사람은 못 씀. SQL을 잘 아는 사람도 다시 배워야.
  • 도구 생태계 좁음. 거의 모든 BI 도구가 SQL을 받지만 Malloy를 직접 받는 곳은 없음.
  • 커뮤니티 작음. 2.5k stars / 5,083 commits / TypeScript 98%로 핵심 contributor 좁음.
  • 표준화 위치 약함. OSI에 직접 참여하지 않음. dbt Labs/Snowflake/Salesforce가 만드는 표준의 바깥에 있음.
  • 운영 도구 부족. 권한 / saved query / RLS / multi-tenant — 모두 future work에 가까움.
  • "BI 백엔드"보다 "data developer language" — embedded analytics나 production metric API용으로 설계되지 않음.

Lightdash 심층 분석

"dbt 위에 얹는 오픈소스 BI." dbt 모델의 meta: 블록에 dimension / metric을 정의하면 자동으로 BI 화면이 떠오른다. 시맨틱 레이어는 부산물이고, 1차 정체성은 BI 도구.

철학과 trade-off

Lightdash의 선택: "Looker의 대안, 단 dbt-native + 오픈소스." dbt 프로젝트에 이미 있는 모델 + tests + 문서를 BI 첫 번째 시민으로 끌어올린다. 정의는 YAML, 시각화는 UI.

  • dbt-native가 모든 것. 시맨틱 정의는 dbt 모델 YAML 안의 meta: 블록.
  • Git PR workflow. KPI 변경 = PR 리뷰. 코드형 거버넌스.
  • BI UX 우선. Explore / Dashboard / 자연어 쿼리 인터페이스.
  • 모든 게 self-hosted 가능. Cloud 옵션도 있지만 Apache 2.0이라 lock-in 없음.

모델링 언어

파일 포맷은 dbt YAML의 확장. dbt 모델의 column 안에 meta.dimension, meta.metrics를 직접 적는다.

metricsum / count / count_distinct / avg / min / max / median / percentile / boolean — MetricFlow보다 표면이 좁음
joindbt schema.yml에 join 명시. fan-out 회피는 사용자 책임
saved queryUI에서 만든 chart / dashboard로 저장

엔진 아키텍처

알려진 약점

  • multi-tenant / RLS 약함. 엔터프라이즈 기능은 Cloud 유료 plan으로 분리.
  • dbt에 100% lock-in. dbt 없으면 안 돌아감.

11 · SCENARIOS

시나리오별 평가

같은 시맨틱 레이어라도 use case에 따라 best fit이 다르다. 우리가 어떤 시나리오에 가까운지부터 정직하게 짚는다.

시나리오 A — 메트릭 정의 + 검증 + 다중 차원 dispatch 중심

"한 manifest에 metric 50–500개, dimension 100+, 다양한 grain에서 dispatch. 정확성이 최우선."

Best fit: MetricFlow. 5종 metric type + entity-based auto-join + metric_time + 28개 validation rule이 다른 어떤 후보보다 깊다. Cube는 가능하지만 metric 표현력이 평이. Malloy는 새 언어가 부담. Lightdash/Rill은 BI에 묶임.

시나리오 B — BI 대시보드 backend (Tableau/Superset/Looker)

"여러 BI 도구가 같은 메트릭 정의를 공유해야 한다. JDBC/ODBC 호환이 결정적."

Best fit: Cube (SQL API). Postgres wire 호환으로 모든 BI 도구가 그냥 연결. MetricFlow는 dbt Cloud의 JDBC adapter를 거쳐야 — 우리가 직접 만들면 추가 비용. Lightdash는 자체 BI이지 BI backend가 아님.

시나리오 C — 사이트 임베디드 분석 (customer-facing dashboard)

"100–1000 tenant, sub-second 응답 요구, 각 tenant마다 row-level filter."

Best fit: Cube. 이 시나리오는 사실상 Cube가 만들어졌다. pre-aggregation + security context + REST/GraphQL이 결합. MetricFlow는 캐시가 없어 부적합.

시나리오 D — ML/DS 헤드리스 metric API

"Python notebook에서 메트릭을 불러 feature로 사용. 정의가 BI와 일치해야 데이터 사이언티스트가 믿는다."

Best fit: MetricFlow 또는 Cube. MetricFlow는 정확성 + 표현력에서 유리, Cube는 Python SDK + GraphQL에서 유리. Malloy는 SDK 약함.

시나리오 E — 멀티테넌트 SaaS analytics 백엔드

"여러 고객사가 한 인프라를 공유. 각 고객의 데이터 격리 + 별개 metric set."

Best fit: Cube. security context + multi-manifest + 캐시 분리가 표준. MetricFlow는 manifest 수준 격리만 가능 — 운영 코드를 추가 작성해야 함.

CLAUDE.md, FEASIBILITY.md, PROGRESS.md의 단서를 정직하게 모으면:

운영 대상Monomer Control의 Semantic module에 공급하는 시맨틱 코어
책임 경계SQL 생성까지. 실행은 외부 (gRPC contract에 명시)
호출 방식gRPC (8개 RPC: explain · listMetrics · ... · validateManifest)
dialect8개 모두 (Trino · BigQuery · Snowflake · Databricks · Redshift · DuckDB · Postgres · Default)

시나리오로 매핑하면 시나리오 A (메트릭 정의 + 검증 + dispatch) + 시나리오 D 일부 (헤드리스 API)가 압도적으로 가깝다. 시나리오 B/C/E는 우리 책임 경계 밖.

의의. 우리 시나리오가 시나리오 A이면 MetricFlow가 가장 잘 맞는다. 만약 시나리오 C(임베디드 sub-second)였다면 Cube가 명백히 더 적합했을 것. 책임 경계 정의가 이미 base 선택을 거의 결정한 상태였다.

12 · HONEST ASSESSMENT

MetricFlow의 강점과 약점 (정직 평가)

sunk cost가 의사결정을 왜곡하지 않도록, 강점만 모은 listicle을 피하고 약점도 같은 무게로 짚는다.

강점 (이것 때문에 베이스로 좋다)

  • 메트릭 표현력 1위. 5종 metric type(simple · ratio · cumulative · derived · conversion). Cube에 비해 cumulative / conversion이 일급. Malloy는 nest로 가능하지만 cumulative는 비대칭.
  • entity-based auto-join. fan-out / chasm join을 entity type으로 정적으로 회피. Cube가 사용자 책임으로 두는 부분.
  • metric_time + time spine. 메트릭 간 공통 시간 추상화. cumulative 윈도우 자동 처리. 다른 후보 중 가장 정교.
  • 검증 28 rule 풀 셋. 의미 모델 정합성 검사가 다른 후보보다 깊고 명세적.
  • 설계 계층 분리 명확. manifest → spec → dataflow → sql plan → render. Kotlin 포팅이 1:1 매핑 가능했던 이유.
  • OSI 표준의 참조 구현. 2025-10 이후 MetricFlow의 YAML 스키마가 산업 표준(OSI)의 base. 산업 컨소시엄이 같은 추상화를 채택.
  • 오픈소스 라이선스 안정. AGPL → BSL을 거쳐 2025-10에 Apache 2.0 정착. 더 이상 라이선스 후퇴 위험 낮음.
  • SQL 실행 분리. 우리 책임 경계(SQL 생성까지)와 완전히 일치. Cube/Rill처럼 실행 인프라까지 끌고 오지 않음.
  • 2,854 SQL snapshots. upstream에 차등 테스트용 corpus가 이미 있음. 우리 corpus 100% PASS는 우연이 아니라 이 자산의 직접 결과.

약점 (이것 때문에 customize 부담이 있다)

  • 0.x 버전. 1.0 미릴리즈. 0.211까지 갔지만 major 모델 변경 가능성 잔존. 단 OSI 표준화 흐름이 이걸 줄임.
  • 2-hop join limit. MAX_JOIN_HOPS=2 하드코딩. 3-hop 이상 join이 필요한 도메인에 부적합. customize 필요 시 가능 (우리 Kotlin 포팅에서 이 값을 조정 가능).
  • 전역 이름공간. entity / dimension / measure / metric 이름이 manifest 전체에서 unique. 멀티-도메인 manifest 운영 시 prefix 강제 (운영 컨벤션으로 회피).
  • pre-aggregation 없음. 쿼리 시점 SQL 생성만 — sub-second 요구는 외부에서 풀어야. (단 우리 책임 경계 밖이라 약점이 아님.)
  • API 표면 좁음. Cube의 REST/GraphQL/MCP 같은 풍성한 API가 없음 — SQL + 메타만. (단 우리는 gRPC로 감싸므로 큰 문제 아님.)
  • BI 도구 직결 약함. dbt Cloud의 JDBC adapter를 거치는 게 표준 — 우리가 BI backend로 쓰려면 추가 인프라 작성. (단 우리 책임 경계 밖이라 약점이 아님.)
  • dimension은 primary entity가 있는 model에서만. primary key 없는 event log는 dimension으로 직접 join 불가. 다른 entity로 우회 필요.
  • 학습 곡선. entity / measure / metric / metric_time / time spine 같은 어휘를 다 익혀야 함.

우리 포팅 자산 (이게 결정에 어떻게 들어가나)

포팅 자산 자체는 결정 논거가 아니다 (매몰비용). 하지만 다음은 진짜 의미를 가진다.

  • 학습 가독성 정책의 산물. Kotlin 코드가 metricflow 도메인 어휘 보존 + KDoc + 모듈 README로 작성되어 있어 customize 시 "어디를 만져야 하는지" 명확. 다른 base로 갈아타면 이 가독성 자산은 사라진다.
  • corpus 100% PASS는 customize의 안전망. 한 번 깨질 때마다 즉시 회귀가 보고된다. 다른 base에는 이 corpus를 다시 만들어야 함.
  • OSI 흐름과의 정렬. 우리 포팅이 OSI 참조 구현의 JVM 버전으로 정확히 위치함 — Python에서 JVM으로 가는 표준 진입점이 됨.

13 · STAY OR PIVOT

우리 상황 분석 — 머무를까 갈아탈까

두 시나리오의 비용을 같은 단위로 추정한다. 답이 동률에 가까우면 매몰비용이 결정한다고 판단할 근거가 약해진다.

시나리오 X — 머무른다 (MetricFlow customize 계속)

예상 비용:

  • customize 항목별로 +mission cycle. 평균 cycle당 ~300–400k 토큰 (Phase 3 평균).
  • corpus 회귀가 안전망 — 매 변경마다 강한 신호. 추가 인프라 작성 0.
  • OSI 표준이 진화하면 upstream sync mission으로 따라잡음. 0.211 → 0.220 정도의 마이너 sync는 1–2 mission cycle.

예상 위험:

  • 1.0 미릴리즈 — major model 변경이 발생하면 추격 cycle 부담. 단 OSI 흐름이 model을 묶음 → 변동성 낮아짐.
  • customize가 깊어지면 upstream과 divergence. fork friction.

시나리오 Y — 갈아탄다 (예: Cube로 피벗)

예상 비용:

  • 8.6M 토큰 매몰. 60k LOC 포팅 + 28 validation rule + 8 dialect renderer + corpus 인프라 폐기.
  • Cube의 핵심 코어가 Rust (Cube Store) + Node (Cube Server) — JVM 포팅 자체가 metricflow보다 복잡. Rust 코어를 그대로 두고 JVM client만 만들면 우리 책임 경계 (SQL 생성까지)가 깨짐 — Cube 클러스터를 띄워야 함.
  • Cube의 모델 (cube + view + explicit join)이 MetricFlow의 모델 (semantic_model + entity + metric)과 다름. 기존 yaml 마이그레이션 필요.
  • corpus 재구축. Cube에는 우리 같은 2,854 snapshot이 없음.

얻는 것:

  • pre-aggregation으로 sub-second 응답 가능 — 단 우리 책임 경계 밖.
  • REST/GraphQL API — 단 우리는 gRPC 가지고 있음.
  • 임베디드 분석 표준 — 단 우리 사용 케이스가 임베디드가 아님.

시나리오 Z — 다른 base로 갈아탄다 (Malloy / Lightdash / Rill / BSL)

Malloy로 새 언어 도입 + nested data 강점. 단 멀티-dialect SQL 생성기로의 의도가 약하고, 운영 도구 (RLS, multi-tenant, saved query 깊은 표현력)가 약함. 비추천
Lightdash로 Lightdash는 BI 도구이지 시맨틱 엔진 라이브러리가 아님. 우리 책임 경계와 어긋남. 부적합
Rill로 OLAP에 묶임. warehouse 직접 쿼리 환경에서 어색. 부적합
BSL로 표현력 미흡 + 성숙도 낮음. 라이브러리로서는 신생. 부적합

비용 비교 도식

주의. 위 비용 추정은 단순 토큰 견적이고, 갈아탐의 진짜 비용은 시간 + 모멘텀 손실 + 학습 가독성 자산 폐기. 토큰 견적은 그 그림자에 불과.

14 · RECOMMENDATION

결론 및 권장

MetricFlow를 그대로 간다. sunk cost를 빼고 봐도 베이스로서 가장 잘 맞는다. 다만 customize 방향에는 우선순위가 있다.

권장 — 머무름, 단 OSI 표준화 흐름에 맞춰 정렬

  1. OSI 표준 정렬을 1순위로. 2025-10 이후 MetricFlow의 YAML 스키마가 OSI 참조 구현. customize 시 OSI 호환을 깨지 않는 방향으로 (uplift는 OK, 의미 변경은 NO). 우리 포팅이 자연스럽게 OSI 표준의 JVM 참조 구현으로 위상이 격상됨.
  2. upstream sync를 정기 mission으로. 0.211 → 0.220 → … 마이너 sync를 분기마다 1개 mission cycle. PROGRESS.md에 sync 항목을 별도 row로.
  3. customize는 운영 코드(application/engine)에 우선. domain 계층(manifest/spec/dataflow/sql)에 customize 가하지 말 것. upstream sync 비용 폭증. 새 RPC, 캐시, 권한, telemetry는 application 계층에서.
  4. 차등 테스트 corpus를 자산으로 유지. 운영 trace를 추가로 캡처해 corpus를 키워두면 customize 안전망이 더 두꺼워짐. harness/sql_norm/rules/에 normalizer 규칙을 명시 보존.
  5. 2-hop join 같은 알려진 제한은 customize 후보로 보관. upstream이 lift 가능성 있음 (OSI에서 논의). 우리가 먼저 가지 말 것 — divergence cost.

권장 이유 5가지

1. 책임 경계 일치 SQL 생성까지가 우리 책임. MetricFlow가 같은 경계로 설계됨. Cube/Rill처럼 실행 인프라까지 끌고 오지 않음 → 우리 사용 케이스에 맞음
2. 표현력 1위 5종 metric type + entity-based join + metric_time + 28 validation rule. 이 깊이를 customize로 다른 base에 추가하면 비용 폭증
3. OSI 참조 구현 2025-10 OSS + OSI 표준화로 거버넌스가 dbt Labs 단독에서 산업 컨소시엄으로 이동. 표준 진화의 흐름에 무료로 올라타게 됨
4. 포팅 자산 매몰비용이 아닌 학습 가독성 + corpus 100% + 도메인 어휘 보존이라는 진짜 자산. 갈아타면 사라짐
5. 갈아탐의 비대칭 비용 Cube는 책임 경계 다름, Malloy는 새 언어, Lightdash/Rill은 BI. 어디로 가도 우리 use case와 결이 어긋남

customize 우선순위 (1년 plan 제안)

  • Q1. Phase 5 마무리 (internal sweep + gRPC split). 외부 publishable JAR + BOM. Maven publish 준비.
  • Q1. upstream sync 0.220까지. OSI 스키마 변경 흡수.
  • Q2. Phase 4: integration examples (dbt → Kotlin 엔진 → warehouse 차트). 데모 앱.
  • Q2. 운영 telemetry / metric usage analytics (application 계층, domain 무변경).
  • Q3. customize candidate 1: MAX_JOIN_HOPS lift (OSI에 제안 먼저, 받아들여지면 upstream PR. 안 받으면 우리만 적용 + normalizer로 흡수).
  • Q3. customize candidate 2: 운영 corpus 확장 (운영 trace 캡처 → corpus 합류).
  • Q4. Monomer Control Semantic module의 versioned artifact 채택.

한 줄. Kotlin 포팅이 단순한 "MetricFlow의 JVM 사본"이 아니라 OSI 표준의 JVM 참조 구현으로 승격되었다는 게 이 분석의 가장 큰 발견. 매몰비용이 자산으로 바뀐 순간이다.
